# 按改动影响选择测试

目标是尽快发现真实产品问题并交付，不是扩大测试数量。测试按模块和风险类型组织，不因隔了一天或准备发布就机械重跑全部用例。

## 选择范围

- **共享游戏逻辑**：存档、角色控制、交互状态、经济或岗位流程、共享碰撞与寻路。验证被修改的逻辑、边界状态和直接依赖它的关键路径；共用引擎发生变化时，再覆盖受影响地区
- **局部场景与几何**：单个门、楼梯、池体、家具。检查该对象的碰撞、相邻物体、入口净空和相关交互；用正常游玩镜头查看正反面及必要的边界姿态。不重跑无依赖的国家或系统
- **人物姿态或临时外观**：只选能暴露问题的性别/体型/服饰边界，验证骨骼接触、进入/退出恢复和存档身份保持。不穷举无关外观组合
- **颜色与纯装饰**：默认用有代表性的实际渲染和人工审图，不为单个颜色值、装饰数量或静态材质常量额外建立自动回归。若改到共享 shader、透明混合或材质生命周期，再按其实际影响扩大范围
- **构建与部署**：修改构建、缓存或资源组织时验证资源引用与更新兼容；每次发布做轻量版本、公开访问和关键入口检查，不把它变成完整游戏重测

## 不重复做已完成的检查

同一验证版本的相关代码、依赖和环境没有改变，可引用原结果。只因某个无关文件、文档、提交号或日期变化，不使已有结果失效。几何/材质哈希可用于证明某批次没有修改其他地区，但不为所有静态属性长期堆积快照断言。

全量测试适用于确实横跨多个系统的修改、引擎/依赖升级或有证据的集成风险，不是每天或每个小修复的固定门槛。

## 新增自动测试的门槛

新增前说明它能复现哪类真实缺陷、为何可能再次发生，以及它覆盖哪些依赖。优先保留稳定、低成本、能定位原因的用例。一次性美术评估、重复证明同一事实和容易误报的几何检查不自动升级为永久发布门槛。

失败先区分产品缺陷和检查工具缺陷。工具自身有歧义时，用直接场景证据交叉确认，不为了让检查“全绿”放宽产品标准，也不无限扩建验证框架。

## 每批交付

在变更记录或 checklist 中简记：改动模块、选择的检查及原因、复用的已有证据、通过/失败/未运行，以及仍存在的风险。足够验收的独立批次及时上线；与其无关的未完功能继续留在测试分支。
